# agriLease — Model Card

This document describes every trained model in agriLease as of this pass: what data it was trained on, how it was validated, its actual measured accuracy, and — just as importantly — what it can't do and why. Numbers below are copied directly from the training scripts' output (`scripts/ml/data/*.json`), not rounded up or cherry-picked. Where a model performs weakly, that is stated as plainly as where it performs well; a lower/negative R² or an RMSE that doesn't beat a naive baseline is reported because it's true and because *why* it's true is itself informative.

All training is reproducible: every script is in `scripts/ml/`, every dataset (except the ~90MB raw FAOSTAT download, regenerated by one documented command) is committed alongside this card.

---

## 1. Crop Yield Prediction

**Replaces**: the previous hash-based heuristic in `src/lib/ai/yield.ts` (kept as a documented, honest fallback — see §1.6).

### 1.1 Data

- **Target (yield, kg/ha)**: [FAOSTAT](https://www.fao.org/faostat/en/#data/QCL) "Production: Crops and livestock products" bulk dataset, `Element = Yield`, filtered to 5 crop items matching this app's `CropType` enum: `Wheat`, `Barley`, `Olives`, `Citrus Fruit, Total`, `Vegetables Primary`. `OTHER` has no single representative FAOSTAT item and is not trained on (see §1.6).
- **Features (avg_temp_c, total_precip_mm)**: [NASA POWER](https://power.larc.nasa.gov/) monthly climate API, real historical data for the *exact country and year* each yield row belongs to (not a long-term climate normal) — one API call per country (17 countries, chosen for climatic/crop diversity: Morocco, Spain, France, Italy, Greece, Egypt, Tunisia, Algeria, USA, India, Australia, Argentina, Canada, Russia, China, Brazil, South Africa), aggregating that country's monthly values into annual figures per year, 2000–2023.
- **A feature that was tried and dropped**: FAOSTAT's "area harvested" (a country-level aggregate, millions of hectares for large producers) — not a meaningful predictor of one field's per-hectare yield rate, and not something a farmer using this app could ever supply as an input. Documented in `scripts/ml/train_yield_model.py`'s docstring.
- **Final dataset**: 1,892 rows across 5 crops (`scripts/ml/data/yield_training_data.csv`), built by `scripts/ml/build_yield_dataset.py`.

### 1.2 Model

One **gradient-boosted regression tree ensemble** per crop type (`GradientBoostingRegressor`, 200 estimators, max depth 3, learning rate 0.05, scikit-learn), rather than one pooled model with crop-type dummies — yield scales differ by an order of magnitude between crops (vegetables ~20,000 kg/ha vs. wheat ~2,000 kg/ha), and this app always knows a field's crop type up front.

A plain linear regression was trained first, for comparison, and it fit far worse (see §1.3). The GBM model — not the linear one — is what's served.

### 1.3 Results (held-out 20% test split, per crop)

| Crop | n (train/test) | Linear R² | Linear RMSE | **GBM R² (served)** | **GBM RMSE (served)** |
|---|---|---|---|---|---|
| Wheat | 326/82 | 0.020 | 1549.4 | **0.663** | **908.5** |
| Barley | 326/82 | 0.106 | 1196.0 | **0.505** | **890.1** |
| Olives | 230/58 | -0.075 | 2802.0 | **0.332** | **2207.8** |
| Citrus | 304/76 | 0.082 | 6396.8 | **0.458** | **4912.3** |
| Vegetables | 326/82 | 0.095 | 6259.5 | **0.399** | **5099.7** |

**Read honestly**: even the served GBM model explains at best ~66% of held-out yield variance (wheat) and as little as ~33% (olives). The linear model is markedly worse — for olives its R² is *negative*, meaning it predicts worse than just guessing the mean every time.

**Why this is expected, not a bug**: this dataset spans 17 countries with wildly different irrigation infrastructure, farming technology, seed varieties, and mechanization levels — factors this model has no visibility into. Two climate features (temperature, rainfall) capture only part of what actually drives cross-country yield differences; the agricultural economics literature consistently finds climate alone is a weak yield predictor at this scale. A model trained on *one region's* historical yields against its own climate would very likely fit tighter — that's a legitimate direction for future work (see §1.6), not attempted here given this pass's scope and time budget.

### 1.4 Serving architecture

Training happens **offline in Python** (this repo has no Python runtime in production). The trained GBM's full tree structure (every split feature/threshold/child node, every leaf value, the learning rate, and the initial prediction) is exported to `src/lib/ai/yieldModel.json` and re-implemented as a plain tree-traversal function in `src/lib/ai/gbm.ts` — no ONNX runtime, no Python process, at request time.

**This port was checked for exact parity, not assumed correct.** `scripts/ml/train_yield_model.py` also exports 20 real held-out test rows plus scikit-learn's own `.predict()` output for them (`scripts/ml/data/gbm_parity_check.json`); `tests/gbm-parity.test.ts` runs the TypeScript port against those same rows and asserts the outputs match. **This caught a real bug**: an earlier version rounded each tree's split threshold to 6 decimal places on export, which is fine for display but not for a value a `<=` comparison branches on — a feature value that legitimately sat between the true (float64) threshold and the rounded one took the wrong branch in a handful of cases, silently producing a materially different prediction (one row was off by ~700 units out of ~2,200). Fixed by exporting full float64 precision for thresholds and leaf values (only the top-level reported metrics are rounded, since those are for display, not computation).

### 1.5 Live inference inputs

At request time (`src/lib/ai/yield.ts`), the model is fed **the field's own real recent climate**: the trailing 365 days of NASA POWER daily data (temperature, precipitation) for that field's exact coordinates, aggregated the same way training data was (mean daily temp, summed precipitation) — not today's forecast, and not a generic regional average.

### 1.6 Fallback and honesty in the UI

- `OTHER` crop type: always uses the original hash-based heuristic (documented in `src/lib/ai/yield.ts`) — no trained model exists for this catch-all category.
- If the live NASA POWER climate fetch fails: falls back to the same heuristic rather than breaking the page.
- Every `YieldPrediction` carries a `modelBacked: boolean` field, and the UI (`YieldFieldCard.tsx`) visibly labels which predictions are model-backed vs. a fallback estimate — this is never hidden from the user.

**Future work**: train separate models per-region rather than pooling 17 countries together (should substantially improve R²); add soil and fertilizer-use features once a broader real dataset covering those is identified; consider FAOSTAT's "Fertilizers by Nutrient" domain as an additional real feature source.

## 2. Equipment-Task Recommendation

**Replaces**: falls back to, rather than fully replaces — the original keyword-matching heuristic (`src/lib/ai/recommendations.ts`) is retained and used whenever the classifier's confidence is too low or its required inputs aren't available.

### 2.1 Data — synthetic, and why

There is no public dataset of "which equipment type a real farm actually rented for a given task" — this is generated data, produced by `scripts/ml/generate_synthetic_data.py`, and labeled as such everywhere it's referenced (never presented as observed data).

The generator is not arbitrary noise: it encodes real agronomic patterns as *probability distributions* (see `equipment_distribution()`), then samples from them — a genuine, imperfectly-separable classification problem rather than a lookup table with extra steps. The one deliberately-encoded real distinction: olive harvesting in practice typically uses a tractor-mounted shaker/net, not a combine harvester the way wheat/barley harvest does — the generator gives olives a 75% tractor / 25% harvester split at harvest, versus wheat/barley's 60–85% harvester split (size-dependent). 800 rows generated (`scripts/ml/data/synthetic_equipment_recommendation.csv`).

Features: `crop_type` (5 types, one-hot), `task_type` (5 categories: plowing/spraying/harvesting/transport/irrigation, derived from the same keyword rules the fallback heuristic uses), `farm_size_ha` (log-normal distributed, 0.5–500ha), `month`.

### 2.2 Model

A `RandomForestClassifier` (200 trees) was trained for comparison. A single `DecisionTreeClassifier` (max depth 6) is what's actually **served** — this app has no runtime for a 200-tree ensemble vote without meaningfully more serving complexity, and a single tree's accuracy is close enough to the forest's on this dataset that the simplicity is worth it, *especially* combined with the confidence-based fallback described below.

### 2.3 Results (held-out 20% test split, 160 rows)

| | Accuracy | Macro F1 |
|---|---|---|
| Random Forest (comparison only) | 0.713 | 0.630 |
| **Decision Tree (served)** | **0.644** | **0.543** |

A single tree gets ~64% of held-out rows exactly right. This is the expected consequence of *deliberately* overlapping classes in the generator (e.g. a tractor genuinely is sometimes the realistic choice for a spraying task, not a labeling error) — a real classification problem, not a memorization exercise, and not perfectly separable by design.

### 2.4 Serving and the documented fallback

`src/lib/ai/recommendations.ts`'s `idealTypeSource()`: tries the classifier only when the task has a linked field with a known crop type covered by the model, a farm size, and a scheduled date; if the classifier's leaf-node confidence (the majority class's share of training samples at that leaf) is below **0.5**, or any required input is missing, it falls back to the original keyword-matching rule — never silently returns nothing, and the UI's reasoning text says "(trained model, NN% confidence)" only when the model was actually used, so a farmer can tell which recommendations are model-backed.

The tree port was parity-checked the same way as the yield model's (`tests/equipment-classifier-parity.test.ts`, `scripts/ml/data/equipment_classifier_parity_check.json`) — this one passed on the first run, having already learned from the yield model's rounding bug to export full precision from the start.

## 3. Equipment Demand Forecast

**Adds to, rather than replaces**: the existing field-specific, hours-needed forecast (`forecastDemand`'s `weeks` output — driven by each farmer's own fields' crop types and harvest dates) is unchanged. A new, clearly separate `platformSeasonalTrend` field is added alongside it.

### 3.1 Data — synthetic, and why

No real historical rental data exists for this platform yet (it's not in production). `scripts/ml/generate_synthetic_data.py` generates 6 years of synthetic weekly rental counts per equipment type, with seasonal spikes tied to each crop's typical planting/harvest calendar (the same real-world timing patterns the pre-existing rule-based forecast used), **plus year-to-year timing jitter** (±2 weeks, modeling real weather-driven variation in when a season actually starts) and Poisson-distributed noise around the seasonal signal.

### 3.2 Model, and a real negative result that shaped it

Per the brief, this uses the simplest reasonable time-series approach: for each (equipment type, ISO week-of-year), the model is that week's mean historical rental count — a seasonal climatology, the same technique this project already uses for weather normals.

**The first version of this model was evaluated and found to not work, and that finding changed the design, not just the writeup.** Trained on 2 years of data with the raw per-week mean (no smoothing), evaluated on a third held-out year: **RMSE 1.99, versus 1.53 for a naive baseline with no seasonality at all** — the seasonal model was *worse* than ignoring seasonality. Root cause: with only 2 training years and ±2-week timing jitter built into the generator, a single week's 2-sample average mostly captures noise, not a stable season.

Fix: 5 training years instead of 2 (more samples per week), and a **±2-week moving-average smoothing** pass over the per-week table (matching the generator's jitter window) — turning "guess the exact week" into "detect the elevated-demand season," which is both what a moving average is for and what the underlying real-world signal (weather-shifted harvest timing) actually supports.

### 3.3 Results, reported honestly

| | RMSE | MAE |
|---|---|---|
| Seasonal model (served, ±2wk smoothed, 5 training years) | 1.361 | 1.097 |
| Naive baseline (no seasonality) | 1.332 | 1.051 |

**The smoothed seasonal model is still not conclusively better than the naive baseline on this synthetic dataset** (RMSE within ~2% of each other) — reported as-is rather than tuned further to force a better-looking number, which would risk overfitting the evaluation itself. The likely explanation: at the demand *amplitude* configured in the generator, the Poisson sampling noise floor is large relative to the seasonal signal, so point-forecast accuracy alone doesn't show much daylight between "seasonal" and "flat."

**Why it's still served anyway**: the model's value here isn't primarily the point forecast — it's surfacing *which weeks and equipment types* tend to run busier, shown as a relative "busier/quieter than usual" multiplier (`platformSeasonalTrend`) rather than an absolute count, and kept visibly separate from the field-specific hours-needed numbers rather than blended into them (blending two different signal types — hours-needed for *your* fields vs. a platform-wide relative trend — into one number would misrepresent both). The chat assistant (§4) surfaces this as "platform-wide rental history also suggests week X tends to run busier."

**Future work**: once this platform has real booking history, retrain on that instead of synthetic data — real demand won't have an artificially-injected jitter window, and the smoothing window itself should be tuned against real seasonal transition sharpness rather than assumed to match the generator's own parameter.

## 4. Chat Assistant

Unchanged in mechanism — still keyword/regex intent classification with templated replies (`src/lib/ai/assistant.ts`), not an LLM, exactly as documented in `PROJECT_REPORT.md` §8.4. What changed this pass: its answers are now grounded in the live/trained data above rather than only static rule-based numbers:

- Yield answers now say whether a figure is "trained model, fed this field's recent climate" or a fallback estimate.
- Demand-forecast answers now mention the trained platform-wide seasonal signal alongside the field-specific hours forecast.
- Two new intents were added: **WEATHER** (live Open-Meteo conditions for the farmer's primary farm, including frost/heat risk) and **SOIL** (live SoilGrids composition) — both explicitly say when data is unavailable rather than fabricating an answer, and both correctly report a farm's genuine "no soil survey coverage here" state (a real condition observed near coastlines/urban areas during Phase 2) distinctly from a fetch failure.

A full LLM-based conversation remains a stretch goal, not implemented, exactly as scoped.

## 5. Reproducing all of this

```bash
# Yield model (real data)
curl -o scripts/ml/data/Production_Crops_Livestock_E_All_Data_NOFLAG.csv \
  <extract from https://bulks-faostat.fao.org/production/Production_Crops_Livestock_E_All_Data.zip>
python scripts/ml/build_yield_dataset.py     # ~5 min (17 NASA POWER API calls)
python scripts/ml/train_yield_model.py

# Equipment recommendation + demand forecast (synthetic data)
python scripts/ml/generate_synthetic_data.py
python scripts/ml/train_equipment_classifier.py
python scripts/ml/train_demand_forecast.py
```

Each training script writes its served model JSON directly into `src/lib/ai/`, and its metrics/parity fixtures into `scripts/ml/data/` (both committed). Re-run `npm test` afterward — `tests/gbm-parity.test.ts` and `tests/equipment-classifier-parity.test.ts` will catch any TS/Python mismatch in the served model immediately, the same way they caught the rounding bug described in §1.4.
